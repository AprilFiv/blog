## 高层次的分布式系统
```success
分布式系统是用多台电脑解决一台电脑就能解决的问题的手段
```
任何一台电脑都需要完成这两个任务
- 存储
- 计算

分布式系统是用多台电脑解决一台电脑就能解决的问题的手段-通常是因为这个问题不再适合用一台电脑去解决。

没有什么是必须要用分布式系统去解决的。假设给你无限的金钱和研发时间，我们就不需要分布式系统。所有的计算和存储可以在一个盒子里完成-一个非常快，非常可靠的系统。

然而，基本没有人有无限的资源，因此，他们不得不在现实世界里寻找支出-受益曲线的平衡点。在规模较小时，升级硬件是一种显而易见的选择。但是，但问题的规模逐渐升级，你会发现单纯的升级一台机器的硬件已经无法解决问题，或者此时升级的成本已经非常高，在这个节点上，分布式系统的世界将会为你打开。

目前的现实，中档的商品硬件具有最好的价值-我们只要使用合适的容错软件，就可以降低维护成本。

高档硬件的主要受益功能是计算，在某种程度上它们可以用内存来代替缓慢的网络传输。而它们的性能受限于需要大量节点实例进行网络交流的任务。

![avatar](http://book.mixu.net/distsys/images/barroso_holzle.png)

如图所示，在假设所有节点都具有相同的内存访问方式的前提下，高端硬件与商品硬件（中档）的性能差距随着集群大小不断缩小。

理想情况下，增加一个节点会线性增加系统的性能和容量。但显然这是不可能的，联结分开的计算机这将会产生一些开销，如数据必须复制，计算任务需要进行协调等，这也是为什么学习分布式算法是值得的-它可以对具体的问题提出有效的解决方式，什么样的实施方式花费最小等等。

这本书所讨论的分布式系统是一种通俗的，但商业相关的设定：数据中心。如，我不会讨论因为跨国网络产生的具体问题，会一些设置了共享内存产生的问题。另外，本书重点是讨论系统的设计，而不是优化一种具体的设计。

### 我们想要做到的：可扩展性和其他的好处

我所看见的，一切都是因为要处理对应的规模而产生了需求。

许多事情在规模很小时很琐碎-相同的问题在它超过某个特定的规模，体积或者一些物理限制之后会变得更加难以解决。举起一块巧克力很容易，举起一座山很难。很容易计算一个房间里有多少人，很难统计一个国家有多少人。

因此一切都是源于规模-可伸缩性。非正式地说，在一个具备伸缩能力的系统中，当我们把它的规模从小扩大，事情并不会递增的变糟糕。如下是另一个定义。

```javascript
可扩展性是一个系统，一个网络，或一个进程在应付工作量的增加时具备应对的能力，或者说他自身可以变大去契合这种工作量的增加。
```

工作量的增加是指什么？你可以用任何一种增长来衡量，如人口增加，电量增长等。但是这里有三种特别有趣的。

- 规模可扩展性：增加节点应该线性地让系统变快，增加数据集不应该增加延迟。
- 地理可扩展性：可以使用多个数据中心来减少每次用户查询的响应时间，同时用合理的方式来处理跨数据中心带来的延迟。
- 管理可拓展性：增加更多的节点不会增加系统的管理开支。

当然，在现实的系统中，增长会同时发生在许多维度，每一种指标只能衡量增长的某些方面。

一个可拓展的系统应该能够持续的适应用户规模的增长，有两个相关的方面-性能和可用性。

```javascript
性能（延迟）：一定时间和一定资源条件下系统能够完成的有效工作。
```

根据如上的定义，这会包括如下的几个方面：

- 小工作量下的低延迟或者少的响应时间。
- 高吞吐量（完成工作的速度）
- 较低的计算机资源使用率

在优化这几个方面时必须有权衡。比如，一个系统为了达到大吞吐量，一次性处理大量的工作来减少操作的开销，这时，响应时间就会因批量处理而增大了。

低延迟（响应时间短）是性能表现最有趣的一个点，因为他和物理资源有着非常强的联系。相比较于其他几个性能表现，它用金钱去解决是非常困难的。

关于延迟有许多具体的定义，但我非常喜欢etymology中的定义。

```javascript
延迟（Latency）：处于等待状态的时间，创建某个东西到它完成的这段时间。
等待（Latent）：根据拉丁词典，存在的但是还未激活的。
```

这个定义实在是太帅了，因为他具切的阐明了延迟就是当某些东西发生直到它可见的这段时间。

假设，你被一种空气传播的病毒感染了，这种病毒会把人变成僵尸。延迟就是你感染病毒到你真正变成僵尸的这段时间。

我们假设我们的分布式系统正在处理一个高水平的任务，给它一个查询任务，他会调用系统的全部数据去计算出一个结果。换句话说，分布式系统就是一个数据存储中心，他会调用一个确定的函数用现有的数据去解决问题。

```javascript
result = query(all data in the system)
```

因此，延迟无关于旧数据的多少，而是一个新数据生效所需要的时间，如，延迟可以用一个写操作生效，用户可读来衡量。

反过来说，根据如上定义，如果一个系统数据不会发生改变，那他就不存在延迟，也就不会有延迟的问题。

在一个分布式系统中，有一个最小延迟是无法跨越的，光的传播速度决定了信息的传送速度，硬件元件间就会有一个最小的延迟成本。

这个最小的延迟是多少取决于你查询操作的性质以及物理设备的距离。

### 可用性（容错能力）

可拓展系统的第二个方面是可用性。

```javascript
可用性：系统处于运行状态时所占的比例。如果用户不能访问系统，则被认为是不可用的。
```

分布式系统允许我们去做到一些单机系统无法做到的理想特性，如：一个单机系统没有任何容错能力，一旦它挂了，它就是挂了。

分布式系统用一堆不可靠的组件，去建立一个可靠的系统。

无冗余存储的系统只要在他们的底层硬件可用时可用，但是一旦系统去做一些冗余存储，他们就将具有一定的容错能力，从而变得更可用。值得注意的是，“冗余”的意义会根据你的需求而变化-组件，服务器，数据中心等等。

如果将可用性公式化

```javascript
Availability = uptime / (uptime + downtime)
```
从技术视角来说，可用性意味着容错能力。因为宕机的可能性会随着节点数量增加而增加，系统需要具有补偿能力，否则就会因为节点数的增加而变得越来越不可靠。

可用性 % | 一年内会有多少服务不可用的时间
---- | ---
90% ("one nine") |	超过一个月
99% ("two nines") |	小于四天
99.9% ("three nines")	| 小于九小时
99.99% ("four nines") |	小于一小时
99.999% ("five nines") |	~ 5分钟
99.9999% ("six nines") |	~ 31秒

可用性在某种意义上是比服务时间更加宽泛的概念，因为可用性还可能被如网络中断，服务提供商退出服务（与容错能力无关，但是与可用性有关）等因素影响。但是既然我们不能知道我们系统的方方面面，那就只能去设计好他的容错能力了。

那么容错能力是什么呢？

```javascript
容错能力：一旦错误发生，系统能够以既定的方式运行的能力。
```

概括地说，定义可能发生的错误，然后设计一个系统或者方法允许它发生。你不可能去兼容一个你从未定义过的错误。

### 是什么阻止我们往好的方向发展？

分布式系统被如下两个物理因素限制着：
- 节点数量（他可以增加容量和计算能力）。
- 节点间的距离（信息传播，最好的情况下是光速）。
